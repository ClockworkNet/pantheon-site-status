# Recommendations: Fix vs. Replatform

## Bottom line

**Fix in place, don't replatform.** The system is small (~1,300 lines total across Dart + Vue), its bugs are shallow and specific rather than architectural, and the two frameworks in use (Nuxt/Vue, Dart) are outdated but not broken. A rewrite would cost far more than the fixes below and would re-introduce the same class of bugs unless the underlying process (tests, review) changes too. The one item worth treating as urgent regardless of which path you pick is the public exposure of vulnerability data (§3).

## 1. Confirmed bugs to fix

These were verified by reading the code and, where noted, by diffing against git history — not guessed from patterns.

1. **Vulnerable-plugin filter is broken** — [site/pages/sites.vue:114](site/pages/sites.vue:114) filters `plugin.vulnerable !== ""`. The evaluator/Dart model never emits `""`; a non-vulnerable plugin is serialized as the literal string `"None"` ([evaluator/lib/evaluator.dart:96](evaluator/lib/evaluator.dart:96), [evaluator/lib/models/wordpress_plugin.dart:61](evaluator/lib/models/wordpress_plugin.dart:61)). Result: **every plugin on every site is currently counted as vulnerable** in the per-site detail modal. Confirmed via `git log -p`: this line correctly read `!== "None"` as of commit `0228fa6` ("Fixed vulnerable filtering bug") and was later changed to `!== ""`, silently reintroducing the exact bug that commit fixed.
2. **Plugin aggregation keys are wrong** — [site/store/sites.js:18-19](site/store/sites.js:18): `pluginToSiteMap` does `Object.entries(site.plugins)` where `site.plugins` is a JSON **array**, then uses `entry[0]` (the array *index*, e.g. `"0"`, `"1"`) as the map key instead of the plugin's `slug`. Two different plugins that happen to sit at the same index on different sites collide into one bucket, and the same plugin at different indices on different sites is split into multiple buckets. This directly corrupts the Plugins page's per-plugin site/upgrade counts — almost certainly the cause of, or a sibling to, the "wrong counts displayed" issue referenced in recent commit history (`6ecabb8`). Fix: key by `plugin.slug`.
3. **Drupal sites are silently unevaluated** — [evaluator/lib/evaluator.dart:108](evaluator/lib/evaluator.dart:108), `_evaluateDrupal` is an empty stub. Any Drupal site shows zero issues regardless of actual CMS/module health — not a crash, but a false "all clear."
4. **No error/exit-code handling on most Terminus calls** — [evaluator/lib/pantheon.dart](evaluator/lib/pantheon.dart): only `fetchWordPressPlugins` checks `result.exitCode`. `fetchPhpVersion`, `fetchLiveUrl`, `fetchNewRelicStatus`, `fetchUpstreamStatus`, `fetchWordPressVersion` all trust `result.stdout` unconditionally. A failed/timed-out Terminus call (expired token, site down, rate limit) silently produces an empty string that then flows into the evaluator as if it were real data (e.g., empty PHP version → "Unknown" stability, logged as fine).
5. **Misleading doc comments describing caching that doesn't exist** — [evaluator/lib/pantheon.dart:27,40](evaluator/lib/pantheon.dart:27) say "trying the cache first" / "if there is cached data, it will be used." There is no cache anywhere in the codebase. Either implement it (see §2) or remove the comments so nobody trusts them.
6. **Leftover debug output in production code**: `console.info('filtered updated')` in [site/pages/sites.vue:123](site/pages/sites.vue:123), `console.info(newValue)` in [site/components/pages/sites/Header.vue:57](site/components/pages/sites/Header.vue:57), and `console.info(event)` in [site/components/pages/sites/Table.vue:219](site/components/pages/sites/Table.vue:219) — the last one references the deprecated global `window.event` rather than the row-click argument, so it doesn't even log what it looks like it's trying to log.

## 2. Recommended hardening (not bugs, but worth doing alongside the fixes)

- **Parallelize per-site enrichment.** `_enrichSites` in [evaluator/lib/sinfo_manager.dart:66](evaluator/lib/sinfo_manager.dart:66) awaits each site's ~5 sequential Terminus subprocess calls one site at a time. For an org with dozens of sites this is the dominant cost of the daily run. Batching sites with `Future.wait` (with a concurrency cap to avoid hammering Terminus/Pantheon's API) would cut runtime substantially with low risk.
- **Pin the Dart install in CI.** [.github/workflows/update-sinfo.yml:29-36](.github/workflows/update-sinfo.yml:29) pulls `dart_stable` fresh via `wget`/`apt-key` on every run — unpinned, slow, and one upstream change away from breaking the pipeline silently. Switch to `dart-lang/setup-dart` action with a pinned version, mirroring what was already done for Terminus (`pantheon-systems/terminus-github-actions`).
- **Add tests around the two bugs above.** There's an existing Dart test (`evaluator/test/models/site_test.dart`) but nothing on the Vue side and nothing covering plugin evaluation/aggregation — which is exactly where both confirmed bugs live. Even a handful of unit tests on `pluginToSiteMap` and the `sites.vue` computed properties would have caught both regressions before merge.
- **Finish or drop the in-progress Docker buildchain.** The README's "In Progress Work" section (Docker-based buildchain, unresolved Terminus auth) is half-built and not wired into CI. Either finish it or remove it so it doesn't look like a supported path.

## 3. Security note — treat this as higher priority than the tech-stack question

The generated JSON (including which specific plugins are vulnerable, on which sites) is synced to an **S3 bucket with `--acl public-read`** and served via CloudFront ([.github/workflows/update-sinfo.yml:63-66](.github/workflows/update-sinfo.yml:63)). Combined with bug #1 above (which currently *overstates* vulnerabilities, but once fixed will *correctly* report them), this means real, current vulnerability information about client sites will be published on the public internet with no authentication. Recommend restricting the bucket/distribution (e.g., signed CloudFront URLs, an allowlist, or moving it behind login) regardless of whether you fix or replatform — this is independent of the tech-stack decision and shouldn't wait on it.

## 4. If you still want to replatform

If there's a reason beyond these bugs to replatform (team skill mix, wanting to fold this into a larger internal tool, etc.), that's a reasonable call to make — but on the evidence here the current stack isn't the problem. If you do go this route:

- Vue 2/Nuxt 2/Vuetify 2 are all past end-of-life (Vue 2 EOL was Dec 2023); Nuxt 3 + Vuetify 3 (or a lighter stack like plain Vite + a table library) would remove the `NODE_OPTIONS=--openssl-legacy-provider` workaround currently required to build ([site/package.json:7](site/package.json:7)) and get back onto a supported line.
- Keep the Dart evaluator's shape (fetch → enrich → evaluate → serialize) — it's a sound, simple ETL pipeline; the bugs are in application logic, not architecture. A rewrite in another language would need to reproduce the same terminus-CLI-shelling approach unless you also fund building against Pantheon's actual API, which is a materially bigger project.
- Either way, fix §1 and §3 first — those are correctness/security issues that exist independent of framework choice, and replatforming without fixing the underlying logic error would just reproduce bug #1 and #2 in new syntax.
